# max-bridge

У мессенджера MAX нет ни публичного API, ни документации к нему. Зато есть веб-клиент `web.max.ru`, который открывает WebSocket и говорит с сервером своим бинарным протоколом. Мост цепляется именно к этому сокету — и дальше разговаривает с MAX напрямую, а не через кнопки.

Результат — MAX внутри Telegram Mini App: чаты, история, медиа, реакции, стикеры, каналы с комментариями, поиск, уведомления в бота.

## Почему не проще

Первая версия читала внутреннее хранилище Svelte-клиента и угадывала имена полей: `senderId` вместо настоящего `sender`, `reactions` вместо `reactionInfo`, `status`, которого там вообще нет. Работало это ровно так, как заслуживало: вместо любого сообщения показывался плейсхолдер «Сообщение», а любая реакция после перезапуска превращалась в 👍. Один и тот же корень объяснял добрую половину багов.

Сейчас история, реакции, отправка, удаление, поиск и подписки идут по протоколу. Что снято с живой сессии — записано в [docs/max-protocol.md](docs/max-protocol.md): 33 опкода, раскладка кадра, формы вложений.

Из отдельно дорогих находок: msgpack с `useBigInt64` пишет большое **обычное** число как float64. MAX на такой кадр не ругается — он аккуратно закрывает соединение с кодом 1000. Выглядит как «сокет умер», ищется долго. Курсор истории теперь принудительно уходит в int64.

## Как устроено

```
apps/web      React-мини-апп в Telegram
apps/api      Fastify: сессии, маршруты, SQLite, бот
apps/worker   Playwright: по headless-Chromium на пользователя
packages/core          домен на TypeBox, строгие схемы
packages/max-adapter   разбор кадров MAX в домен
packages/protocol      контракт api ↔ worker
```

API и воркер живут в разных процессах и общаются через unix-сокет `/run/maxbridge/worker.sock`. Пользовательские записи в SQLite лежат зашифрованными; ключи подаёт systemd через `LoadCredential`, в репозитории их нет и быть не должно.

237 файлов исходников, 76 файлов тестов. `npm run verify` прогоняет lint, typecheck, тесты и сборку — этим и стоит проверять перед деплоем.

## Запуск

Нужен Node 22+.

```bash
npm ci
npm run verify
```

Переменные окружения (в проде их ставит systemd-юнит, локально — `.env` или окружение):

| Переменная | Что это |
|---|---|
| `MAXBRIDGE_HOST` / `MAXBRIDGE_PORT` | где слушает API, по умолчанию `127.0.0.1:3100` |
| `MAXBRIDGE_DATABASE` | путь к SQLite |
| `MAXBRIDGE_WORKER_SOCKET` | unix-сокет до воркера |
| `MAXBRIDGE_PUBLIC_ORIGIN` | публичный origin мини-аппа, он же проверяется в CORS. Только `https` и только корень — иначе API не стартует |
| `MAXBRIDGE_BOT_ENABLED` | поднимать ли Telegram-бота |
| `MAXBRIDGE_ADMIN_TELEGRAM_ID` | кто одобряет новых пользователей. Обязательная, без неё API падает на старте |

Ключи шифрования (`master-key`, `lookup-key`) API читает из каталога, который подсовывает systemd в `CREDENTIALS_DIRECTORY`.

## Деплой

Релиз — это tar-архив собранного дерева. Установщик распаковывает его в `/opt/maxbridge/releases/<timestamp>-<sha>`, ставит зависимости, скачивает Chromium и переключает симлинк `current`:

```bash
npm run build
tar --exclude-vcs --exclude=node_modules -czf /tmp/maxbridge-$REL.tar.gz apps packages ops package.json package-lock.json
scp /tmp/maxbridge-$REL.tar.gz root@<host>:/tmp/
ssh root@<host> "bash /opt/maxbridge/current/ops/scripts/install.sh $REL /tmp/maxbridge-$REL.tar.gz"
ssh root@<host> "systemctl restart maxbridge-workers maxbridge-api"
```

`$REL` обязан выглядеть как `20260807T170020Z-27ba1a3` — установщик проверяет формат и откажется ставить архив с путями наружу или несобранное дерево. Старый релиз никуда не девается, откат — `ops/scripts/rollback.sh`.

Юниты: `maxbridge-api`, `maxbridge-workers`, `maxbridge-cloudflared`.

## Что здесь хрупкое

Стоит знать заранее, потому что это не «недоделки», а плата за отсутствие API.

**Часть действий идёт через интерфейс MAX, а не по проводу.** Отправка вложений, действия с чатом (заглушить, закрепить, очистить, удалить) и пересылка кликают по настоящим кнопкам в headless-браузере. Отправку вложений уже перевели на идентификаторы иконок из спрайта (`#icon_attachment`, `#icon_image`, `#icon_file`, `#icon_send`) — они не зависят от языка интерфейса. Действия с чатом всё ещё ищут пункты меню по русским подписям и сломаются, если MAX отрисуется на другом языке. Это надо доделать.

**Ссылки на медиа живут недолго.** Воркер получает у MAX временный URL и отдаёт байты через свой маршрут с проверкой владельца. Хендл, выданный клиенту, стабилен для конкретного вложения — иначе перечитывание истории переименовывало бы всё подряд и клиент получал бы 404 на то, что только что показывал. Так и было.

**Один пользователь — один Chromium.** Памяти это ест столько, сколько ест Chromium, и линейно по числу активных сессий. Для десятка человек нормально, для тысячи — нет.

**Своей реакции на посте канала в истории не приходит.** MAX её там просто не отдаёт: в `reactionInfo` есть счётчики, а `yourReaction` нет. Веб-клиент, судя по всему, дотягивает её отдельно; мы пока показываем как есть.

## Тесты

```bash
npm test          # vitest, unit + интеграционные
npm run test:e2e  # playwright
npm run lint
npm run typecheck
```

Отдельно стоит посмотреть `tests/security/cross-user.test.ts` — он проверяет, что чат одного пользователя не достаётся другому ни через маршрут, ни через WebSocket. Схемы домена в `packages/core` строгие: лишнее поле в объекте роняет разбор, и это сделано намеренно — чужие данные не должны просачиваться в ответ мимо схемы.
